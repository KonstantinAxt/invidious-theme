# invidious-theme

A custom CSS theme for [Invidious](https://github.com/iv-org/invidious), giving its stock Crystal/ECR-rendered frontend a Material Design 3 look — inspired by [Materialious](https://github.com/Materialious/Materialious) and built directly on [Beer CSS](https://www.beercss.com/) (the actual library Materialious itself is based on).

This is **not** a port of Materialious's code — Materialious is a separate Svelte/Vite single-page app with no code-level overlap with Invidious's server-rendered templates. This repo maps Material Design 3 color roles, shape, and elevation onto Invidious's *existing* HTML structure and class names via hand-written CSS, **and** loads Beer CSS's own real component stylesheet (`vendor/beer.min.css`) for its actual button/checkbox/radio components — see [Component CSS](#component-css) for what that required (a global reset to fix around, and markup changes in the `invidious` fork for checkboxes/radios). Color roles come from Beer CSS's own color engine (see [Design tokens](#design-tokens)).

## Usage

`theme.css` is loaded as an additional `<link rel="stylesheet">` right after Invidious's own `default.css`, `vendor/beer.min.css` loads between that and `theme.css` so `theme.css` keeps the last non-`!important` word in the cascade (see [Component CSS](#component-css)). `vendor/beer.min.js` and `vendor/material-dynamic-colors.min.js` are loaded via `<script type="module">` tags in `<head>`, after those links. See [`KonstantinAxt/invidious`](https://github.com/KonstantinAxt/invidious), branch `materialious-theme`, for the integration (added as a git submodule at `assets/css/invidious-theme`; the `<link>`/`<script>` tags live in `views/template.ecr`, and `assets/js/themes.js`'s `setTheme()` is patched to add Beer's own bare `light`/`dark` body class alongside Invidious's `light-theme`/`dark-theme`/`no-theme` one, then re-run Beer's color engine — see [Design tokens](#design-tokens)).

Respects Invidious's existing light/dark toggle (`body.no-theme` / `body.dark-theme`) — it does not introduce a separate theme switcher. Beer CSS's own `ui("mode", ...)` API is deliberately never called, to avoid two independent scripts fighting over `body.className`.

## Scope

Covers essentially every page that loads Invidious's own `template.ecr` layout: top nav, search field and filters (including real Beer radio/checkbox components), buttons (including plain `.pure-button` confirmation dialogs), form controls (real Beer checkbox/radio and select components, plus CSS-only styling for text/date/etc. inputs and textareas — not range/file, which keep native styling), links, video/channel/playlist cards (including a 2-line-clamped, hover-to-expand headline), typography, feed navigation (Popular/Trending/Subscriptions/Playlists/History), channel page tabs and description, the watch page (player accent color, comments — the same treatment also covers community posts and single post views, which reuse the comment template), and account/playlist management pages (preferences, login, playlist create/edit/delete, subscription/token managers, etc.).

**Exception**: `watch.ecr`'s `#descexpansionbutton` and `#music-desc-expansion` checkboxes stay on native markup, deliberately. `default.css` drives their description/lyrics expand-collapse via `:checked` general-sibling selectors (`#descexpansionbutton:checked ~ div`, etc.) — Beer's checkbox component requires wrapping the input in a `<label class="checkbox">`, which would break that sibling chain and kill the toggle's *function*, not just its look. Every other checkbox/radio in the codebase was confirmed (by grep) to have no such CSS dependency before being converted.

The video-js player's control bar/menus keep their stock skin — only the interactive accent (progress/volume fill, big-play icon, loading spinner) is retinted, not a full skin rebuild. The embed page and the standalone JS-license page are separate HTML documents that don't load this stylesheet at all, so they're structurally out of reach rather than just unstyled.

## Component CSS

`vendor/beer.min.css` (v5.0.3, same version as the JS files) is Beer's real component stylesheet, vendored verbatim. It is **not scoped** to Beer's own classes — it carries a global reset (`*{margin:0!important}`, every bare `<a>`/`<button>` forced to specific defaults, etc.) that applies to every element, not just the ones we want restyled. That was a deliberate, known tradeoff (real Beer fidelity over a `@scope`-wrapped or pre-neutralized reset) — expect to find and fix more collisions with Pure CSS as pages get exercised. Collisions found and fixed so far, all in `theme.css`:

- **Headings**: Beer assigns bare `h1`-`h6` its own MD3 display/headline type scale (`h1` → 57px, `font-weight: 400`) and only restores `margin-block-start` (top), not bottom. Invidious uses heading tags semantically, not for visual hierarchy (`h3` for the comments-count line, `h5` for a related-video's channel name) — restored the standard relative size/weight/margin scale.
- **File inputs**: Beer's `input[type=file]{opacity:0;position:absolute;...}` assumes its own `.file` wrapper component (a visible custom button with the real input invisible on top). Applied to Invidious's bare file inputs (`/data_control`), it just made them invisible and pulled them out of flow. Restored native visible/static styling.
- **Search bar**: Beer's bare `form{display:flex}` turned `.searchbar .pure-form` into a flex row without setting `align-items`, top-anchoring the input instead of centering it in the pill. Added `align-items: center`.
- **Checkbox/radio alignment**: Pure's `.pure-form-aligned .pure-control-group label{text-align:right;width:10em}` (designed for the old separate `label`+`input` markup) still matches Beer's wrapper `<label class="checkbox">`, right-aligning the *whole* icon+caption pairing in a fixed box instead of just caption text — the icon's position drifted per row depending on caption length instead of forming a column. Given its own box model (`width:auto`, left-aligned, shifted to match where other rows' controls start).

Checkboxes/radios needed markup changes, not just CSS, because Beer's checkbox/radio CSS only targets a `<label class="checkbox"|"radio"><input><span>text</span></label>` wrapper — it has no rule for the `<input><label for="...">` sibling pattern Invidious used everywhere. `search_filters.cr`, `preferences.ecr`, and the `continue` checkbox in `watch.ecr` (in the fork) were restructured to that wrapper; see the [Scope](#scope) exception above for what wasn't. Bare `<button>` needed no such change — Beer fills/colors it by default (`:is(button,.button):not(.chip,.fill,.border){background-color:var(--primary);color:var(--on-primary)}`).

Beer's checkbox/radio/switch icons render via a ligature-based icon font (`--font-icon: "Material Symbols Outlined"`), not raster/SVG — the four `vendor/material-symbols-*.woff2` files are required for that, self-hosted because this instance's CSP is `font-src 'self' data:` (no CDN fallback).

`<select>` had the exact same all-or-nothing problem as checkboxes/radios: a bare `<select>` gets zero styling from Beer, real select styling only exists inside a `<div class="field label border"><select>...</select><label>Caption</label></div>` wrapper, and `<select>` immediately before `<label>` as siblings is load-bearing (`select+label` adjacent-sibling CSS, no `:has()` fallback). Every `<select>` in `create_playlist.ecr`, `watch.ecr`, `edit_playlist.ecr`, and `preferences.ecr` (in the fork) was restructured to that wrapper. Two follow-on fixes in `theme.css`:

- **Field width**: `.field` is `display:flex` with no width of its own, so it stretched to its container's full width instead of shrinking to the select's content like a bare `<select>` used to. Fixed with `display:inline-flex` on standalone (non-grouped) fields.
- **Checkbox/radio alignment, again**: the checkbox/radio margin-left from the prior fix targeted where a `<select>` *used to* sit (label-left, control at a fixed offset in Pure's aligned-form layout). Now that selects are Beer `.field` boxes starting flush left themselves, that target position is gone — the margin is removed entirely rather than pointed at a new offset, since flush left is now correct for both.

Beer's `.field` is strictly 1:1 with one control, with no multi-select variant — `preferences.ecr` has a few rows where several selects share one row (`comments`/`captions`/`feed_menu`/`admin_feed_menu`, one per priority/rank). Only the *first* select in each of those rows keeps the row's shared `<label>`; the rest get a labelless `.field.border` — repeating the caption on every select would lose the "this is the Nth choice" ordering the row exists to show. They're grouped in a plain flex row (`.pure-control-group.multi-field` in `theme.css`) since Beer has no built-in layout for that. `edit_playlist.ecr`'s privacy select has no `<label>` at all in the original markup (plain text, not a `<label>` element), so it only gets `.field.border`, no `.label`.

## Design tokens

Primary accent (seed color): `#2596be` (Materialious's own default `themeColor`). Every other color role — `--primary`, `--on-primary`, `--surface`, `--surface-variant`, `--outline`, etc. — is generated from that seed by Beer CSS's own color engine, [material-dynamic-colors](https://github.com/leonardorafael/material-dynamic-colors), the same real HCT-based Material color science Beer CSS's `ui("theme", ...)` uses internally.

`vendor/beer.min.js` and `vendor/material-dynamic-colors.min.js` are Beer CSS's real files (v5.0.3 / v1.1.4), vendored verbatim, self-hosted rather than CDN-loaded (Invidious serves all its own assets locally — no third-party requests on page load). There's no separate bootstrap script — `themes.js`'s `setTheme()` (in the `invidious` fork) calls `ui("theme", "#2596be")` itself, every time the theme changes (initial load, toggle click, cross-tab sync, or the OS scheme changing while in "no-theme"/auto mode). That call computes the palette and writes it as **inline styles directly on `body.style`** (not a separate stylesheet) — it has to re-run on every change, since it reads the current light/dark class to decide which variant to write, and stale inline values would otherwise pin the old colors after a toggle.

**`ui("theme", ...)` is a silent no-op if called before the page has fully loaded** — verified live: identical calls fail 100% of the time from `DOMContentLoaded` (even deferred by a macrotask), succeed 100% of the time after the `load` event. No thrown error, no rejected promise — `body.style` just never gets written. `themes.js` tracks `document.readyState`/the `load` event itself and defers the very first call until then; every call after that (toggle, storage sync, OS-scheme change) runs immediately since the page is long past `load` by then. If you ever touch this logic, re-verify with a real `--primary` read on `body.style.cssText`, not just `getComputedStyle` — the static CSS fallback resolves to the *same numbers* by design, so a computed-style check alone can't tell a real dynamic write apart from the fallback silently not being overridden.

`theme.css`'s own `:root`/`body.dark-theme`/`.no-theme` color values are only a **static fallback** — the exact values that call currently produces, hardcoded so `var(--primary)` etc. resolve correctly during the brief window before the JS call resolves. Inline styles always win the cascade regardless of specificity, so no `!important` is needed once the JS catches up. To retheme, change the seed color in both `themes.js`'s `ui("theme", ...)` call and the fallback block at the top of `theme.css` (re-run the color engine to get matching fallback values).

Shape and elevation (`--md-radius-*`, `--md-elevation-*`) are our own hand-picked values — Beer CSS's color engine doesn't cover those, so they're unaffected by any of the above.
